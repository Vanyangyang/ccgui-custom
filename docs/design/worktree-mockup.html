Worktree 功能 · 产品交互设计稿

CC GUI · v1 方案 · 参考 Orca 裁剪 · 2026-09-23 · 设计评审用，非最终实现
痛点：开源项目维护者需要同时审查多个 PR。单工作区下切分支会互相干扰，只能串行处理。 方案核心：每个 PR（或分支）一个 git worktree = 侧栏里挂在主仓库下的子工作区， 各自拥有独立的 AI 会话、终端、变更面板——物理隔离，真正并行。
场景 1

侧栏：Worktree 作为子工作区

worktree 不是新概念，而是「工作区的子节点」——挂在父仓库行下、可展开各自的会话线程。 注册后复用现有全链路：会话、终端 ⌘J、变更面板、文件树上色全部自动可用，零额外适配。

交互要点

  • 层级：父工作区（main 检出）→「WORKTREES · n」分组 → worktree 子行 → 各自的会话线程。子行缩进 + 分支图标，与父级普通会话区分。
  • 行内信息：分支名为主名；PR#n 徽标仅「从 PR 创建」时显示（紫色）；●n 表示未提交变更文件数（橙，30s TTL 缓存，复用 git store）。
  • 入口：WORKTREES 分组标题的 ＋、父工作区行 ⋯ 菜单、右键菜单「新建 Worktree…」（⌘⇧N）三处汇聚到同一个创建对话框。
  • 折叠：worktree 子行可折叠/展开其会话列表；整组「WORKTREES」也可折叠（状态持久化）。
  • 激活态：点击 worktree 行 = 切到该工作区（蓝色高亮），其会话进页签条；路径 chip 提醒当前会话归属哪个 worktree。
  • 数据：workspaces 表恢复旧版 kind + parentId 先例（db.rs 导入逻辑当前跳过它们），meta 存 {branch, prNumber?, baseRef}。
  • 待定 ① 父工作区归档/移除时，其 worktree 子节点是级联提示还是静默保留？倾向级联提示（弹窗列出受影响 worktree）。
场景 2

创建对话框：三种来源，一个入口

核心痛点流程是第一个 Tab——「从 PR 创建」。输入 PR 号或粘贴 GitHub 链接即可， 无需 GitHub 登录/token：同仓 PR 直接 checkout 其分支；fork PR 走 git fetch origin pull/N/head:pr-N，GitHub 原生支持。

交互要点

  • 三个来源 Tab：从 PR 创建（默认选中，痛点主流程）/ 新分支 / 检出已有分支。Tab 只影响「分支从哪来」，下半部分公共。
  • PR 解析预览卡：输入合法后立即显示标题/作者/增删行/将使用的分支名。标题来自 gh CLI（若已安装）；没有 gh 时预览降级为「PR #1842 · 将通过 pull/1842/head 获取」，不阻塞创建。
  • 分支名推导：PR → pr-N-slug；新分支 → 用户输入；冲突（分支或目录已存在）→ 行内红字报错让用户改，不做 Orca 的 25 次自动重试（我们没有 agent 并发创建场景）。
  • git 细节（借鉴 Orca）：git worktree add --no-track -b <branch> <path> <base> + 写 push.autoSetupRemote=true，避免 status 误报 behind。
  • 提交即后台化：⌘↵ 或点击后对话框立即关闭 → 侧栏出现进度行（场景 3）。大仓库 fetch 不阻塞 UI。
  • 待定 ② 默认目录：同级 <repo>-worktrees/（本稿）vs 仓库内 .worktrees/（随仓库走、但会出现在 git status 噪音里需 gitignore）。倾向前者。
  • 待定 ③ 是否记忆上次的「位置 / 打开新会话」勾选作为下次默认？倾向记忆（localStorage）。
场景 3

后台创建：即交即走，可取消可重试

创建不阻塞。侧栏 WORKTREES 分组下出现进度行，fetch 大仓库时用户可以继续干别的；失败行内给原因和重试。

ccgui main
WORKTREES · 2
正在创建 pr-1842-fix-crash…
正在 fetch origin pull/1842/head…
⚠ pr-1800 创建失败
PR 不存在或仓库不可达 重试 关闭
pr-1839-docs PR#1839

交互要点

  • 进度行三态：进行中（转圈 + 阶段文案 + ✕取消）→ 成功（行变为正常 worktree 行，若勾选了「打开新会话」则自动激活）→ 失败（⚠ + 原因 + 重试/关闭，行内 role="alert"）。
  • 阶段文案：fetch → worktree add → 注册工作区，逐步替换，让用户知道卡在哪。
  • 取消语义：取消 = 中断当前 git 子进程并清理半成品（已 add 的 worktree 执行 remove，已建分支保留——分支无害且用户可能要）。
  • 失败分类（对齐规范 §5）：可恢复（网络/冲突）给重试；不可恢复（非 git 仓库、PR 不存在）给说明，不给假按钮。
场景 4

删除：安全预检，分级确认

审查完的 worktree 要能放心删。确认框预加载 git status，把「会丢什么」说清楚；默认保守（不删分支），分支清理由用户显式选择。

删除 Worktree「pr-1842-fix-crash」？

~/code/ccgui-worktrees/pr-1842-fix-crash
⚠
  • 2 个文件有未提交变更（src/session.rs、README.md）
  • 1 个提交未推送到远端
  • 分支 pr-1842-fix-crash 未合入 main
同时删除本地分支 pr-1842-fix-crash
未合入 main 的分支删除后不可恢复；不勾选则分支保留在仓库里
该 worktree 的 2 个会话将保留在历史记录中（归档），目录删除后仍可只读查看。

交互要点

  • 预检内容：未提交变更文件数（列出前 2 个文件名）、未推送提交数、分支合入状态。全干净时不显示警告行，只留一句「没有未提交或未推送的改动」。
  • 删除分支默认不勾：对齐 Orca 的 branch -d 保守语义；勾了且有未合入提交时，执行 git branch -D 前在按钮上再确认一次文案变化（「删除 Worktree 和分支」）。
  • 脏目录处理：git worktree remove --force；删除失败的孤儿目录提示「已在 git 中注销，目录可手动删除」。
  • 会话保留：会话历史绑定路径但存储在 CLI 侧，删目录不丢历史；侧栏该 worktree 节点整体移除。
  • 锁定保护：git 层面 locked 的 worktree 菜单里删除项禁用并说明原因（对齐规范「禁用目标不能谎报」）。
  • 进行中保护：有流式会话/运行中终端时，删除前额外确认「该 worktree 有进行中的任务」。
  • 待定 ④ 是否需要 Orca 那种「先改名进回收站再异步删目录」？大目录删除快但实现多一层；v1 倾向直接删（删除走后台任务，不阻塞 UI）。
决策

关键设计决策与 v1 范围裁剪

V1worktree = 子工作区，复用全链路

数据模型恢复旧版 kind/parentId 先例；注册即获得会话/终端/变更面板/文件树能力，不在 UI 里发明第二套「PR 视图」。

依据：RepositorySummary 已识别 linked worktree；git IPC 接受 worktree 内任意路径（repositorySelection.ts）。
V1PR 获取不依赖 GitHub 登录

fork PR 走 git fetch origin pull/N/head:pr-N（GitHub 原生 ref）；PR 标题等元信息在 gh CLI 可用时增强，缺失时降级不阻塞。

依据：你的痛点是「并行审查」，不是「PR 管理台」；拉列表/状态轮询留给 v2。
V1创建后台化 + 冲突报错而非自动重试

对话框即交即走、进度行可取消；分支/目录冲突行内报错让用户改名。

依据：Orca 的 25 次重试 + 名字退役机制是为 agent 并发创建设计的，人工场景是过度工程。
V1删除保守：预检明示 + 默认保留分支

未提交/未推送/未合入三项预检；分支删除显式勾选；locked worktree 禁删。

依据：规范 §6 破坏性操作契约 + Orca worktree-branch-removal 的语义（条件删除防竞态 v1 不需要，人工操作无异步 toast 过期问题）。
V2不做（本轮明确排除）

PR 列表拉取与状态轮询、共享目录 symlink（node_modules）、setup hook、sparse checkout、预热 checkout 池、SSH/WSL/远程主机、archive hook、agent scratch 分类、CLI 等价物。

依据：每一项都对应 Orca 里几十到上百个文件的复杂度；v1 验证主流程后按需补。
待定需要你拍板的 4 个点

① 父工作区移除时 worktree 子节点级联提示（倾向：提示）② 默认目录 同级 <repo>-worktrees/（倾向）vs 仓库内 ③ 记忆上次的位置/勾选（倾向：记忆）④ 删除直接删（倾向）vs 回收站异步删。

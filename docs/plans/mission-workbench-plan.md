# 任务工作台（Mission Workbench）执行方案

> 来源：Codex 会话 `01a0c7e5-0761-7130-8f6b-2c3e508c4a13`（2026-09-22）的讨论结论整理。
> 概念稿：`docs/concepts/mission-native.html`（最终版，含 26 项交互测试 `mission-native.test.mjs`）。
> 本文档面向新窗口直接实施，写清范围、架构、接口、步骤与验收标准。

## 1. 产品目标

用户用自然语言描述目标（例："把这个仓库所有 PR 审查一遍"），AI 自动生成可执行流程并调度运行；人不参与编排，只在需要时通过收件箱做业务决策（审批、补充信息、处理失败）。

核心交互判断：**创作时以流程为中心，执行时以结果和待办为中心**。画布始终可用，但不始终占据首屏。

## 2. 已确认的关键决策（不要再翻案）

| 决策 | 结论 |
|---|---|
| 入口形态 | **原生功能，不做插件**。侧栏「新建浏览器」下方的灰色「自动化」占位项（`src/i18n/zh.ts` 的 `automation` / `automationComingSoon`）替换为「任务工作台」，打开中心页签 |
| 编排者 | **AI 是唯一编排者**。人不能拖节点、连线、手填节点配置；只能观察、定位、通过对话提出修改。人仍处理业务决策（审批/补充信息/重试），走收件箱 |
| 节点三层模型 | ① **节点类型**：我们实现，固定（执行契约）；② **节点定义**：AI 生成（名称、指令、输入输出、参数）；③ **运行实例**：调度器生成（foreach 在运行时展开为 N 个任务实例，30 个 PR 不需要 30 个手写节点） |
| AI 生成什么 | AI 生成**结构化流程描述（JSON）**，不是图片、不是 JSX、不是可执行代码。程序做 schema 校验 + 业务校验后更新草稿，画布只负责渲染 |
| 版本与运行隔离 | 运行保存启动时的规则快照。修改草稿产生新版本，**不悄悄改变进行中的运行**；下一轮运行才应用 |
| 第一版能力边界 | AI 组合**受支持的节点类型与已接入能力**。用户要求未接入的能力（如"发到某系统"）时，正确行为是生成步骤但标注"缺少能力，不可运行"，不伪造能力。不做现场生成并执行任意代码 |
| 安全示例边界 | PR 审查模板只输出审查意见，不合并、不评论、不访问外部系统 |

## 3. 三个核心对象（数据模型）

| 对象 | 回答的问题 | 要点 |
|---|---|---|
| **FlowDefinition（流程/SOP）** | 这类工作应该怎么做 | 有 draft 与版本；含节点定义、连线、并发限制、重试次数、分流条件 |
| **Run（一次运行）** | 这次具体做什么、做到哪了 | 绑定流程版本快照；含任务实例列表、状态、进度、成果 |
| **InboxItem（待办/消息）** | 现在需要我做什么 | 关联具体 run + 节点/任务实例；类型：需人工介入 / 失败 / 已完成 / 普通进度 |

### 第一版节点类型（固定实现，共 6 种）

| 类型 | 作用 | 示例 |
|---|---|---|
| `input` | 提供本次任务的数据与范围 | 仓库、文件、用户填写材料 |
| `tool` | 执行已接入、参数明确的操作 | 获取 PR 列表、读取文件 |
| `agent` | 需要理解/分析/生成的工作 | 审查代码、分类反馈 |
| `foreach` | 对一组数据逐项执行子流程，限制并发 | 30 个 PR 最多并发 5 个 |
| `human` | 保存等待状态，收集批准或补充信息 | 确认结果、补充判断标准 |
| `output` | 保存成果、结束运行、发完成消息 | 审查摘要、需求清单 |

### 任务实例状态机

`queued → running → (succeeded | failed | waiting_human | cancelled)`；`failed` 按规则自动重试，超限进收件箱；`waiting_human` / `failed` **不占并发槽、不阻塞其他实例**；反馈/重试只让对应分支重新执行，不重跑全部；所有分支终结后才生成汇总（`output`）。

## 4. 技术架构

### 4.1 模块位置

- 前端功能：`src/features/mission/`（新目录，遵守项目边界约定）
  - `store.ts` — zustand 状态（流程列表、草稿、运行、收件箱）
  - `components/` — 画布页、流程列表、收件箱、节点详情、对话区
  - `engine/` — 调度器、节点执行器、校验器（纯 TS，可单测）
- 入口接线：`src/features/chat/use-chat-sidebar.ts`（参照 `handleNewBrowser` 的模式新增 `handleOpenMission`）+ `ai-chat-sidebar.tsx` + 中心页签类型
- i18n：`src/i18n/zh.ts`（及对应 en）新增 `mission` 相关文案，沿用现有国际化方式
- 持久化：第一版可用前端 store + 现有存储接口；如需跨重启恢复运行状态，再下沉到 `src-tauri`（Rust/sqlite），作为独立里程碑评估

### 4.2 前端技术选型（已确认）

| 技术 | 负责 |
|---|---|
| React | 对话区、列表、收件箱、状态管理 |
| React Flow | 节点、连线、缩放、选中、详情（自定义节点是固定 React 组件，节点数据决定标题/参数/状态；**不让 AI 生成 JSX**） |
| shadcn/ui | 表单、弹窗、Tabs、消息面板，按需引入并适配宿主主题，不替换宿主 UI |

注意：React Flow 只是画布组件，**不等于任务执行系统**。调度、持久化、等待审批、重试、恢复由我们自己的 `engine/` 运行层实现。

### 4.3 AI 编排链路

```
用户对话 → AI 读取（当前流程草稿 + 能力目录 + 修改要求）
        → 生成结构化流程/修改提案（JSON）
        → schema 校验 + 业务校验
        → 更新草稿（产生新版本）
        → 画布渲染 + 变更摘要
```

- 用 JSON Schema 校验结构（必需字段、类型、允许的节点类型），再做**业务校验**：引用的工具是否存在、上下游输入输出是否匹配、是否有循环/悬空连接、数据源与权限是否就绪、是否含未授权的外部写入。
- **修改而非重画**：保留原节点 ID、已有配置与布局位置，只改必要部分；每次修改向用户展示变更摘要（例："已把人工确认移到汇总之后；其他步骤不变"）。
- 布局：程序自动布局（如 dagre 分层），因为人不手动摆节点。

### 4.4 调度器（engine/ 核心）

- 依赖调度：上游全部成功才放行下游；`foreach` 展开子实例并限制并发槽。
- `human` 节点：挂起实例、写收件箱、保存等待状态；收到决定后恢复。
- 失败：按流程定义的重试次数自动重试，超限生成 `failed` 收件箱项。
- 恢复：第一版至少做到页面内状态完整；应用关闭后的恢复策略在持久化里程碑定义（关闭页签 ≠ 取消运行，需明确语义）。

### 4.5 Agent 执行

复用宿主现有 agent 执行管线（与 plugin-sdk `ctx.agent.start/interrupt` 同一条引擎链路，但原生功能直接调用，不经过插件层）。

**已知缺口**：现有 agent 接口没有逐节点工具白名单。若要求"某节点只读"，需要在原生层为每次 agent 调用加能力约束——这是本方案的一个明确技术任务，不允许用"节点名叫只读"来假装实现。

## 5. 界面结构（对齐 mission-native.html）

中心页签内三个一级入口：

1. **流程编排（studio）**：左侧对话 + 右侧画布（流程定义视图 / 运行画布视图切换）。新用户无任务时展示"描述你的目标"。
2. **流程列表（flows）**：可复用 SOP、草稿、版本管理。
3. **收件箱（inbox）**：筛选（全部/需人工介入/失败/已完成）、搜索；待办卡自带决策上下文（建议、依据、影响），简单决定就地完成（批准/驳回/重试/补充），复杂问题可跳对应节点。已读 ≠ 已处理。

## 6. 分期实施

### M0 — 骨架与数据模型（无 AI）
- 建 `src/features/mission/`，定义 TS 类型（Flow/Node/Run/TaskInstance/InboxItem）。
- 侧栏入口替换「自动化」占位，中心页签打开空工作台（三个入口切换）。
- 验收：`pnpm build` 通过；入口文案走 i18n。

### M1 — 本地引擎 + 模拟执行
- 实现 `engine/`：校验器、调度器、6 种节点执行器（agent 节点先用 mock）、foreach 展开、重试、人工等待、收件箱。
- 内置一份 PR 审查示例流程，可完整跑通"启动 → 并发执行 → 失败重试 → 人工确认 → 汇总"。
- 验收：`pnpm exec vitest run` 覆盖调度器核心用例（并发槽、等待不阻塞、失败重试上限、反馈只重跑分支、快照隔离）。

### M2 — 画布与收件箱 UI
- React Flow 自定义节点（6 种类型对应固定组件），流程定义/运行画布双视图，节点详情面板。
- 收件箱完整交互：筛选、就地审批/重试/补充信息、跳转节点。
- 验收：对齐 `mission-native.html` 的交互行为；补 `tests/` 下回归测试（参照 `node --experimental-strip-types --test tests/*.test.ts` 的方式）。

### M3 — AI 编排接入
- 对话区接入宿主 agent 管线；能力目录 + 结构化提案 + 两级校验；增量修改与变更摘要；自动布局。
- 缺能力时明确标注"不可运行"，不伪造。
- 验收：对话"审查所有 PR"能生成合法流程并可启动；对话修改产生新版本且不影响进行中的运行。

### M4 — 持久化与恢复（可后置）
- 评估并下沉到 `src-tauri`；定义关闭页签/退出应用的运行语义与恢复路径。
- 验收：重启应用后运行状态、收件箱、成果可恢复；取消/中断正确收敛。

## 8. 硬性约束（项目约定）

- 不吞异常、不用假成功隐藏缺口；未接入的能力如实标注。
- 日志不输出凭据与完整用户对话；清理临时调试输出。
- 定时器、订阅、异步任务必须有清理路径；处理卸载、取消、旧任务晚到的更新。
- 文件控制在 500 行以内；输入在系统边界处校验。
- 报告中区分实际通过/失败/跳过/未覆盖，不以构建通过宣称问题解决。

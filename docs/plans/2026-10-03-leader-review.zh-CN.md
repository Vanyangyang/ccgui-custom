# Leader 模式评估与修复（2026-10-03）

## 范围与依据

- 对象：定制版 Leader 的原生协调器 `src-tauri/src/leader.rs`，发送链路 `engine/{mod,reader,registry}.rs`、`host_chat.rs`，
  以及界面 `src/features/leader/*`、聊天页签与会话搜索。
- 用户的产品取舍：Claude/Codex 可以互派真实子聊天并递归委派；只有直属父级管理和回收自己的孩子，回收覆盖整棵子树；
  TTL 到期只提示检查，不自动删除或重试；提示词保留模型对分工的判断。
- 过程：评估先由 Codex 进行，后由 Claude 接续。Spellcast 法阵 `ccgui-leader-review-20261003` 一直停在草稿第 1 版，
  原定的四步只读审查从未冻结、启动、认领或执行。本文是聊天中实际修复与测试的记录，不是法阵执行记录。

## 已确认的问题与修复

1. **回收后剩余页签不加载历史**（界面）。批量回收整棵子树后，剩余页签只被直接设为当前，冷缓存不读历史。
   改为一次关闭整批页签，再走共享的 `activateChatTab` 正常激活；慢读取完成不切回旧页签、不恢复已回收会话。
2. **会话搜索与过期分支**（界面）。没有原生 ID、`selectable:false` 的启动中分支出现在搜索的可打开结果里；
   点击过期的启动中分支会清掉当前中心面。现在搜索过滤这些行，点击过期分支保持当前视图。
3. **独立发送绕过 Leader 登记**（原生）。插件 agent、任务工作台和受限工具发送可以续跑受管会话，却不在 Leader 账本里；
   父级回收只停旧运行，可能删除新进程仍在使用的会话。现在这些发送登记为没有 Leader 调用能力的运行，
   拒绝已启用的根会话、任何子会话、回收墓碑和仍有孩子的根会话，并与归档/删除、启用 Leader 互相围栏；普通无管理关系的会话保持兼容。
4. **自有传输写错事件流**（原生）。Codex app-server 等自有传输硬编码主聊天事件流，插件/任务事件会进入聊天界面。现在传递实际事件流。
5. **合法重试被误拒**（原生）。同一 run ID 的独立重试会先插入新的 pid=0 预留，旧检查把它当成旧的活进程。
   现在只接受本次启动标记（`killed` Arc）拥有的预留，并要求旧账本已经退休。
6. **被拒绝的重试提前退休旧运行**（原生，接续时发现）。旧运行的登记表条目已清空、但 `finish()` 尚未到达时，重试被拒绝；
   该次失败的清理仍调用 Leader `finish`，把旧账本标记为退休。下一次重试因此被放行，旧运行稍后的 `finish` 再把新运行退休。
   现在启动守卫只在本次尝试确实完成 Leader 登记后才退休账本；未登记的失败只撤销宿主中继侧的能力。
7. **托管子聊天的首次身份绑定不原子**（原生，接续时实现）。原流程是校验 → reader 认领登记表别名（rekey）→ 事件观察才提交身份，
   中间隔离发送可以抢先预约同一个原生 ID；rekey 遇到别人的别名还会静默返回，子聊天照样宣布并记录这个会话，回收时会删除别人的会话。
   现在：校验同时在 Leader 里写入对所有围栏可见的“待绑定”预留；rekey 碰撞返回错误，reader 释放预留、撤销能力并报错，不宣布也不记入分支；
   rekey 成功后才提交身份并持久化到分支。
8. **回收开始后才到达的首个身份无人清理**（原生，接续时实现）。回收进行中，CLI 才宣布新会话 ID，旧逻辑直接拒绝，CLI 已写的转录不会被回收删除。
   现在若该 ID 无人占用、别名认领成功，就只记入分支供删除转录，不采用、不宣布，reader 仍以错误结束。

## 设计取舍

- **预留而不是持锁跨 rekey**：不让 Leader 锁包住登记表操作，保持既有的 inner → registry 锁顺序，也不重构通用登记表。
  预留按 run ID 存放，`finish()` 一并清除，即使 reader 中途异常也不会残留。
- **只为托管子聊天的首个身份和独立运行预留**：普通聊天仍由事件观察提交身份，不新增它与独立 agent 之间原本没有的围栏。
- **短暂冲突一律失败关闭**：预留期间的隔离发送、归档/删除、GUI 续跑都直接报错，不自动重试，由调用方决定。
- **rekey 的边界**：同一进程已有的别名（如续跑时预先登记的会话 ID）不算碰撞；来源条目已被清空时视为没有可认领的别名，
  继续提交以便回收清理。
- **重试语义**：旧运行真正退场前一律拒绝同 ID 重试，宁可让客户端再试，也不让两个运行共用一个账本条目。
- **回收中的身份只做清理**：记录它是为了删除子聊天自己的转录；仍然拒绝采用，避免回收中的进程获得新身份或继续对外宣布。
- **真实协调器的集成测试放进子进程**：协调器是进程全局的 `OnceLock`，每个用例用 `--exact` 在独立子进程里运行，
  假删除只记录调用，假 CLI 与隔离 HOME 来自现有 test-harness，绝不触碰真实 HOME、CLI 或聊天。

Windows 11，Rust 1.88，Strawberry Perl 5.32（`PERL` 指向其 `perl.exe`，清除 `CARGO_TARGET_DIR`）。

- `cargo test --lib leader::tests::` 等：Leader 44 项、登记表 rekey 2 项、reader 碰撞 1 项，共 47 项通过。
- `cargo test --features test-harness --test send_path`：12/12 通过（原 9 项 + 3 项子进程真实协调器用例：插件与任务各两轮同 ID 重试；
  被拒重试不退休旧运行、旧运行退场后新运行不被退休；子聊天不认领别人的会话、回收不删除它，认领成功的会话在回收时被删除，墓碑继续拒绝独立续跑）。

- `cargo test --lib` 全量：845 通过、6 忽略、3 失败。3 项都在 `skills_hub`，于创建符号链接处失败（Windows 需要开发者模式或管理员权限），

## 未验证的边界与已知限制

- 没有运行真实 Claude/Codex CLI，也没有验证真实的混合引擎闭环；集成测试使用假 CLI 和假 app-server。
- 定制版 CCGUI 尚未构建安装：本次会话本身由正在运行的 CCGUI 承载，`maint:install` 在发现运行中的 `ccgui-next.exe` 时拒绝安装。
- 若 `kill` 的中止兜底先清空登记表、而 reader 仍在同步认领身份，回收可能在该身份提交前读到“无会话”，转录不会被删除；只留下墓碑围栏。
- 独立运行的 CLI 若先后宣布两个不同 ID，围栏只覆盖续跑 ID 和最后一个 ID（沿用原有语义）。
- 普通 GUI 聊天与独立 agent 同时续跑同一会话时，Leader 不互相围栏（Claude 发送前仍会等待旧进程退场）。

## 法阵在这次评估中暴露的不足

- 用户点击“开始”后，法阵只变成运行中，执行者为空，还要手动复制说明，已授权的工作因此空等。Codex 接入了窗口专用的
  “开始并交给原会话”：固定原编写会话的已验证 Codex 绑定，每轮只投递一次，复用现有回执；投递成功不等于认领或验证。
- 接续后发现并修复：每张法阵卡都会把“尚未开始/已结束/执行者不是原会话/Claude 来源”当成 `role="alert"` 的“投递问题”常驻显示，
  实时刷新还会反复播报；现在生命周期原因交给阶段说明，不能交接的原因以本地化原因码说明，告警节点常驻且只在内容变化时更新。
- 接续后发现并修复：独立法阵入口中的确认对话框挂在 body 上、取不到 Canvas 配色，深色主题下冻结授权里的执行目录、命令和授权说明
  对比度只有 1.0–2.6，浅色主题下“取消”按钮看不见。共享 board 对话框在 Canvas 之外的浅色按钮问题可能也影响其他对话框，本轮只改了法阵对话框。
- 验证：`cargo test -p spellcast-bridge --lib sigil` 54 通过、1 项既有的 `console_probe` 忽略（含新增的“生命周期与归属是原因不是投递错误”）；
  bridge 全量 288 通过、1 项 `observer_runner` 过期测试在并行负载下超时，单独重跑 3/3 通过；`npm run build` 通过；
  `node scripts/check-sigil-card-preview.mjs` 19 组通过、60 张截图——在内存 HTTP 夹具和只提供窗口密钥、端口、事件通道的假桌面壳上运行真实卡片模块，
  覆盖开始并交接、失败重试、不确定回执、已认领、启动后传输失败、Claude 来源回退、启动中销毁，以及中英文、深浅主题、360/1320 px。
  两处新缺陷都先用修复前的构建复现失败，再验证通过。

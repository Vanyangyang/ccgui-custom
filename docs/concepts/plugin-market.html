三个方案怎么选

三个方案共用同一套数据、同一份详情页与「已安装」页；差异在浏览形态。切换上方页签即可对比，安装/更新/收藏/分类/搜索/排序都是可点的。

A 密集表格B 卡片画廊C 分栏快速浏览
浏览形态表头固定：名称 / 开发者 / 安装量 / 版本 / 操作精选大图 + 三列卡片墙左分类栏 / 中列表 / 右实时预览
一屏可见约 8–10 个约 3–6 个列表约 7 个 + 1 个预览
进详情点整行 / 点名称点封面 / 点标题右栏直接看；「查看完整详情」进整页
主要优点信息可比、扫描快、改写现有行组件成本最低商店氛围、能给截图上场、发现性强浏览→决策链路最短，分类沉淀、适合重度用户
主要代价视觉偏工具，截图无处发挥没有截图时封面雷同；实现成本最高三栏在 1100px 窗口偏挤；实现成本中高
依赖新数据无建议插件补截图（索引字段已有，只是没人提供）无
适合默认形态，插件 15+ 仍成立有截图、有运营位时插件 30+ 的重度场景

三个方案都会做的改动（参考稿里确实更好的地方）

  1. 分类从下拉框换成带计数的 chips，一屏可点，少一次展开。
  2. 列表右侧从圆形图标改成带文字的「安装 / 更新到 x.y.z / 已安装」，可点面积和状态都更清楚。
  3. 补齐排序（综合 / 安装量 / 名称）与下载量格式化（万）。
  4. 详情页改为左正文 + 右信息栏：动作挪到标题行右侧，右栏 sticky 常驻。
  5. 详情页给截图缩略图条，README 进正文；没截图时给明确空状态，不留白框。
  6. 列表与详情统一标注更新状态（可更新 → 更新到 x.y.z）。

参考稿里有、我们暂时没有的（先不做，避免假数据）

  • 获赞量 / 收藏总数（♥633）：需要后端全局统计 + 索引字段。个人收藏可以纯本机做（方案里已标蓝点），但没有总数就没有参考稿那种社交证明。
  • 最近更新日期：索引 plugins/<id>.json 里没有时间字段；要这列就得加。
  • 开发者主页 / 关注：索引只有 author 字符串，没有主页链接与关注关系。
  • 试用：插件没有"不安装就能试"的形态，装了就在跑，所以不做。
  • 我们的「安装量」来自 download-counts.json（安装 + 更新次数），文案沿用「安装量」即可，但含义要在文案里说清。
我的建议：A 作为默认浏览形态（改动最小、和现有行组件最接近、表格在插件变多后依然成立）；B 的「精选 + 封面」可以先缩成 A 顶部的一行，等插件普遍提供截图后再升级成完整卡片墙；C 等插件数量到 30+ 再评估——那之前三栏会在 1100px 窗口下把名称和描述都截断。
详情页（右信息栏 + 缩略图条）三个方案共用，建议先落地，它和列表形态不冲突。
